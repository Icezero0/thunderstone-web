# Project boundaries

- `backend/` owns accounts, rooms, persistence and network transport. Keep HTTP parsing in `app/api/`, business operations in `app/modules/<domain>/service.py`, and database operations in repositories. `core/` contains infrastructure shared by those modules.
- `engine/` is the independent TypeScript rules package used by both server and browser. It must not import backend/frontend code, perform HTTP calls, or read databases. The server owns authoritative match state; browser preview calculations are stateless.
- Backend callers use `backend.app.integrations.game_engine.api`. Domain adapters and worker serialization are internal to that integration; implement game rules in `engine/`, not in Python wrappers.
- `frontend/src/pages/<page>/` owns each page's controller, views and CSS. `src/app/` composes browser-wide session state. `src/shared/` contains reusable API, realtime and style primitives and must not import pages. Keep HTML entry files and Vite/launcher configuration in the frontend root.
- `backend/devtools/` owns local setup/battle sandboxes and the effect lab. Only `app/main.py` composes their routers into the application. Formal application modules must not depend on devtools or tests.
- Maintenance commands belong in `backend/scripts/catalog/`, `effects/` or `sandbox/`. Test helpers belong in `backend/tests/support/`; do not import test cases as fixtures. Frozen Python migration references remain under `tests/migration/reference/` until parity tests no longer need them.
- `cards/` contains versioned catalog data, images, reviewed effects and evidence. `data/` contains ignored runtime SQLite files, secrets and backups. Keep historical assets and obsolete records in `archive/`; do not restore retired scaffolding there merely to retain executable copies (Git retains code history).
- Keep README examples and imports current when moving files. Create shared abstractions only when there is an actual shared responsibility.
- The user starts listening services. Use the root `.venv` for Python commands; builds, CLI checks and in-process tests may run without starting a server.
- The user normally verifies frontend visual effects manually in the existing running services. Do not independently capture screenshots or run visual acceptance checks, including through GUI automation or headless browsers. If agent visual verification is necessary, explain why and obtain the user's explicit consent before capturing screenshots or performing that verification. Builds, type checks, CLI checks and in-process tests may continue without visual capture.
