## 当前边界与待办

- 怪物效果仍由人工逐卡核对。已录入的符号结论为 36 条有战利品符号、309 条无符号；其中未明确勾选的词条依据当前约定按无符号处理。审核页的新记录保存在浏览器 `localStorage`，需要定期导出 JSON 再合入正式效果定义。
- 联机层尚无房间、座位与准备状态、持久化对局、局内指令提交或按玩家裁剪的状态与事件。现有 setup／战斗 API 接收完整状态，是本地沙箱；WebSocket 目前只处理鉴权和心跳。
- 正式对局前端尚未建设。当前页面服务于配置、实验和审核；共享引擎提供了战斗预览接口，但还没有完整的玩家操作界面。
- 工作区包含大量尚未提交的 TypeScript 迁移、Python 适配、审核修正及旧引擎移除。进入下一阶段前应先形成可回退的 Git 阶段提交，并确保归档的审核 JSON 已纳入提交。

## 建议的推进顺序

1. **固定当前基线。** 核对生成物和忽略规则，提交已完成的迁移与审核修正；保持效果覆盖审计和现有回归测试通过。
2. **并行处理怪物审核。** 人工继续在 `/monster-audit` 核对卡图与效果，分批导出审核 JSON；每批按能力 ID 与绑定指纹合入规则，并针对实际分歧加行为测试。
3. **做一个可持久化的双人对局纵向流程。** 联机层保存房间、参与者、规则配置和准备版本，冻结配置后调用 setup；为每条局内指令实现认证玩家映射、版本检查、幂等键、原子保存状态与事件。先用内部 API 测试和两名测试用户贯通开局、一个完整回合、断线恢复。
4. **接入玩家视图和实时推送。** 从服务端完整状态生成每个玩家独立的可见状态、合法操作和事件；验证抽牌堆顺序、他人手牌及私有选择不会通过 HTTP 或 WebSocket 泄漏，再通过现有连接管理器推送。
5. **建设正式对局页面。** 在已稳定的房间／对局接口上呈现手牌、大厅、选择窗口和战斗队伍预览，随后完成从开局到结算的双端演练。

怪物逐卡审核与第 3 步的联机层开发可以同时推进；新审核结论进入规则包时，通过引擎版本和回归测试保护正在开发的接口。
