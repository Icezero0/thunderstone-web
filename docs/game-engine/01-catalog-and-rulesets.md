# 卡牌目录与规则包

本文约定静态卡牌资料、组局关系和可执行规则如何进入一局游戏。它们都是**对局开始前编译好的只读输入**；对局中的抽牌堆、供应数量和临时数值属于 [状态模型](02-state-model.md)。

## 1. 三类输入

| 输入 | 主键 | 包含什么 | 不包含什么 |
| --- | --- | --- | --- |
| `CardCatalog` | `card_id` | 分类、系列、标签、卡面文字、静态数值、图片路径 | 实体牌数量、所属玩家、当前攻击合计 |
| `SetupCatalog` | 随机设置牌的 `card_id` | 从分类/标签生成的组映射、少量例外、特征设置动作；默认数量引用 `CardCatalog.initial_copy_count` | 每局实际抽到了哪些组、洗牌结果和类别倍率 |
| `CompiledRuleset` | 能力 ID / 系统规则 ID | 已绑定参数的触发、条件、选择、效果和适用范围 | 原始中文句子直接执行、TTS 物件坐标 |

`CardCatalog` 的导入源是 [`cards.csv`](../../cards/cards.csv)，字段详见 [数据字典](../data-model.md)。命令行引擎可直接读取 CSV；联网后端从 SQLite 载入相同的目录快照，再传给引擎，详见 [数据库设计](../card-catalog-database-design.md)。`SetupCatalog` 在**构建时只从 CSV** 生成组映射、应用小型例外表并发布为版本化只读索引；该索引和 CSV 一起导入 SQLite，默认实例数使用 `initial_copy_count`。TTS 初始存档只用于一次性数据导入及必要的复核，部署和组局均不读取它，**也不要求把 `random_card_id` 加回 CSV**。`CompiledRuleset` 由已审核的规则 JSON 和绑定参数构成；Python 加载规则快照，TypeScript 编译并执行受限 DSL，编译约束见 [能力运行时](06-ability-runtime.md)。

## 2. CSV 到 `CardDefinition`

导入器按 UTF-8 with BOM 读取 CSV，并保持原始编号文本。仅 `slot_kind=front` 的 720 行可成为对局中的正面定义；参考卡和公共牌背是界面资产。类型字段取 CSV 的 `card_type`、`subcategory`、`tags`；英雄的 `subcategory` 是系列，不能把职业标签当系列。

`tags` 用于规则筛选，不要求与卡面文字完全一致。所有英雄牌在原职业标签末尾显式补充“英雄”，民兵和村庄英雄也带该标签；英雄身份统一检查标签，不再通过 `card_type` 推导。卡面腰部文字另存于 `waist_text`，供应类别和实例倍率仍按大分类处理。

数值转换必须逐字段进行。空字符串表示未知或不适用，不等于 `0`。胜利点、光照等允许负值；`wiki_印刷符号` 标出的 `*` 是动态值，需要能力规则在适用时计算。`upgrade_xp_cost` 和 `defeat_xp_reward` 分别供升级、击败奖励使用，不把 `wiki_经验值` 直接送入同一个通用运算。`正文_基础攻击`、`正文_基础魔法攻击` 只是从文字抽出的静态线索，最终战斗值仍由能力和战斗上下文计算。

建议形成不可变的导入结果：

```text
CardDefinition
  card_id, card_type, subcategory, tags, name
  printed: cost, gold, light, weight, hero_level, strength,
           health, victory_points, upgrade_xp_cost, defeat_xp_reward
  dynamic_symbols, ability_ids, image_path
```

每项 `printed` 数据保留 `None` 与整数 `0` 的区别。图片路径从 CSV 的 `image_path` 读取；规则 JSON 中仍有旧 `generated/cards/...` 路径，不可覆盖正式路径。`source_card_id` 和 `tts_card_id` 只用于追溯。

## 3. 从分类与标签生成 `SetupCatalog`

随机设置牌不进入实际参战、购买或计分的牌区。加载器先按确定规则生成组索引，再对少量无法直接匹配的卡应用例外表；不需要逐组手写 183 个设置牌的完整映射。

| 设置牌 | 默认匹配方式 | 当前资料的核对结果 |
| --- | --- | --- |
| `随机|英雄` | 设置牌 `name` = 英雄牌 `subcategory`（系列）；同系列按 `wiki_英雄等级` 排序 | 52 个英雄随机牌均可对应系列 |
| `随机|村庄` | 设置牌 `name` = 村庄牌 `name` | 91 张中 85 张名称直接匹配；其余由名称别名/多成员组例外表解决 |
| `随机|怪物` | 将设置牌名称中的 `・`、`·` 规范成 `|`，与怪物牌腰部 `tags` 的有序组合匹配 | 40 张中 32 张可精确匹配；其余包含地下城特征入口、前缀组、标签翻译别名和色彩龙 |

村庄名称例外是 `TS-0071`、`TS-0078`、`TS-0081`、`TS-0096`、`TS-0104`、`TS-0129`。其中“村庄盗贼”对应两张实际村庄牌“村庄强盗”“村庄扒手”，不能假设一张村庄随机牌只对应一个卡面。怪物 `TS-0021`“怪潮”、`TS-0034`“腐化德鲁伊”、`TS-0035`“虫群”等需要按约定的共同前缀聚合；`TS-0022`、`TS-0036`、`TS-0042` 的设置牌写“野兽”，实际怪物标签写“动物”，由明确别名处理。`TS-0018`“地下城特征”是设置入口，不计作怪物组。

`TS-0043`“龙”单列为色彩龙组：匹配首标签为“龙”、第二标签为白龙/绿龙/蓝龙/红龙/黑龙的怪物；**排除**“龙|类人生物”。后者由自己的随机设置牌选择。“九头蛇|龙”也属于另一组，不能只查是否含“龙”标签。组映射以设置牌 ID 为键，保留匹配方式、成员和来源；有零匹配或意外多匹配时构建失败并输出差异，不静默猜测。

地下城设置池由怪物随机牌和“地下城特征”入口共同组成。抽到特征入口时转入 `地下城特征牌` 池；具体卡面决定随机环境、随机守护者、对应陷阱/宝藏组或继续抽特征。陷阱、宝藏组尽量根据特征名称与实际牌标签匹配，无法直接对应的少量名称也进入例外表；环境互斥、特殊疾病、放逐仪式和雷霆之石位置由已编译设置能力处理。

## 4. 初始化实例数量与本局倍率

已通过一次性导入脚本 [`import_tts_initial_counts.py`](../../archive/legacy-code/import_tts_initial_counts.py) 从 [`TDS_CN.json`](../../game_TTS/TDS_CN.json) 的实际初始牌堆/供应袋读取数量：递归数叶子卡的 `CardID`，以 CSV 的 `tts_card_id` 对应正式 `card_id`，将结果写入 `cards.csv` 的 `initial_copy_count`。脚本已归档；后续构建从 CSV 生成索引，联网组局使用导入 SQLite 的同一份目录快照。英雄通常呈现 6/4/2 张，特殊系列依目录实值。生成的 [`setup_catalog.json`](../../cards/setup_catalog.json) 只存组成员 ID 与特征动作，不另存一份数量。

不能把全存档的 `tts_copy_count` 当成默认供应数量：`TS-0018`“地下城特征”在随机设置牌堆有 10 张、怪物袋另有 10 张，全存档数量为 20；CSV 的 `initial_copy_count=10` 取其设置牌堆数量。该字段是网页版的默认配置，不是不可修改的规则上限。

联机层提交冻结配置时带上 `instance_multipliers`，村庄牌、英雄牌（所有等级共用）和怪物牌各有一个 ×1～×5 的倍率。引擎从目录快照取得 `initial_copy_count`，对这三类牌乘以对应倍率后实例化；其他牌保持默认数量。按主分类应用倍率：带“英雄”标签的村庄牌仍使用村庄倍率，守护者不使用怪物倍率。倍率只属于这一局，不改卡牌定义。玩家初始牌组默认的 6 民兵/2 匕首/2 应急干粮/2 火把是另一项规则配置，不能把四种基础牌的 TTS 库存误当成**每名玩家**的初始数量。

生成后的 `SetupCatalog` 至少含随机牌对应的实际组、匹配依据和特征设置动作；组成员的默认张数按其 ID 从 CSV 获取。验证要求：成员引用现有正面 `card_id`；英雄等级顺序明确；同一实体实例只进一个牌区；随机池耗尽有定义好的结果；能力未编译的组在组局前被报告或排除。

## 5. 规则模式与优先关系

第一阶段使用 `classic` 竞争模式，对应《飞龙尖塔》规则书第 2～20、24 页的标准流程；既有文档中的 `standard_competitive` 指同一基础规则配置。联机层提交的[冻结规则配置](00-engine-boundary.md)可修改默认组数或固定选中部分牌组，这些属于组局参数，不创建一种新的战斗模式。基础规则、具体卡牌、场景/环境以及选定扩展共同形成 `ruleset_profile`。规则书第 20 页允许具体卡牌覆盖通则；覆盖应以显式的替代规则或设置修改记录来源，而非在核心函数里散落卡牌 ID 判断。

例子：

- 通常只选一张雷霆之石，放在地下城牌堆底部 10 张中；`TS-0198`“飞龙尖塔”使用两个地下城、两张雷霆之石；`TS-0199`“放逐仪式”强制使用全部七张雷霆之石和末日之心，并调整摆放与终局。
- `TS-0034`“腐化德鲁伊”、`TS-0035`“虫群”、`TS-0148`“希德”被选中时，使用特殊疾病牌堆。
- 合作与单人玩法分别使用新的模式配置；它们修改抽取数量、资源所有权或胜负判定，不应通过标准模式里的临时布尔开关混合实现。

## 6. 构建与版本固定

目录准备过程为：加载 CSV → 根据分类/标签与例外表生成并验证 `SetupCatalog` → 将 CSV 和索引显式导入 SQLite。联机运行时从数据库获取目录快照，再编译系统与卡牌规则、生成兼容性报告及不可变的 `catalog_version` 与 `ruleset_version`。TTS 数量导入是此前的一次性资产迁移，不是构建步骤。版本应与实际 CSV、规则输入和编译器版本关联；每局保存这两个版本、选定的规则模式和完整的冻结组局配置，旧对局重放时加载原版本。

规则 JSON 目前与 CSV 有已知差异：722 条旧图片路径、`TS-0717`/`TS-0718` 的显示文本，以及公共牌背类型。名称、标签、二级分类和已核对的 13 项静态数值一致。构建器应输出差异报告：CSV 掌管展示资料，已确认的系统裁定掌管规则语义；不可静默改写 CSV。原 JSON 的 `cards[].abilities[].ast` 是草案位置，`is_executable_as_card_ability=true` 也不等于已通过编译。

## 7. 组局准入

一个配置可以只开放部分随机牌，也可指定固定组并让其余名额随机补足。必须在组局前验证固定组以及随机候选可能选出的**全部实际卡牌**都有可用定义、所需能力已编译且对应系统规则存在。无法满足时明确报告卡牌 ID、能力 ID 和缺少的参数/处理器；不能开始后再跳过某张牌的效果。
