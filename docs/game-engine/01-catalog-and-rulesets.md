# 卡牌目录与规则包

本文约定静态卡牌资料、组局关系和可执行规则如何进入一局游戏。它们都是**对局开始前编译好的只读输入**；对局中的抽牌堆、供应数量和临时数值属于 [状态模型](02-state-model.md)。

## 1. 三类输入

| 输入 | 主键 | 包含什么 | 不包含什么 |
| --- | --- | --- | --- |
| `CardCatalog` | `card_id` | 分类、系列、标签、卡面文字、静态数值、图片路径 | 实体牌数量、所属玩家、当前攻击合计 |
| `SetupCatalog` | 随机设置牌的 `card_id` | 随机设置牌与实际牌组的对应、每组成员及供应数量、特殊设置条件 | 每局实际抽到了哪些组、洗牌结果 |
| `CompiledRuleset` | 能力 ID / 系统规则 ID | 已绑定参数的触发、条件、选择、效果和适用范围 | 原始中文句子直接执行、TTS 物件坐标 |

`CardCatalog` 从 [`cards.csv`](../../data/cards.csv) 读取，字段详见 [数据字典](../data-model.md)。`SetupCatalog` 是后续新增的规则资料，**不要求把 `random_card_id` 加回 CSV**。`CompiledRuleset` 由规则 JSON 草案、人工裁定和 Python 已注册的原子处理器构建，编译约束见 [能力运行时](06-ability-runtime.md)。

## 2. CSV 到 `CardDefinition`

导入器按 UTF-8 with BOM 读取 CSV，并保持原始编号文本。仅 `slot_kind=front` 的 720 行可成为对局中的正面定义；参考卡和公共牌背是界面资产。类型字段取 CSV 的 `card_type`、`subcategory`、`tags`；英雄的 `subcategory` 是系列，不能把职业标签当系列。

数值转换必须逐字段进行。空字符串表示未知或不适用，不等于 `0`。胜利点、光照等允许负值；`wiki_印刷符号` 标出的 `*` 是动态值，需要能力规则在适用时计算。`upgrade_xp_cost` 和 `defeat_xp_reward` 分别供升级、击败奖励使用，不把 `wiki_经验值` 直接送入同一个通用运算。`正文_基础攻击`、`正文_基础魔法攻击` 只是从文字抽出的静态线索，最终战斗值仍由能力和战斗上下文计算。

建议形成不可变的导入结果：

```text
CardDefinition
  card_id, card_type, subcategory, tags, name
  printed: cost, gold, light, weight, hero_level, strength,
           health, victory_points, upgrade_xp_cost, defeat_xp_reward
  dynamic_symbols, ability_ids, image_path
```

每项 `printed` 数据保留 `None` 与整数 `0` 的区别。图片路径从 CSV 的 `image_path` 读取；规则 JSON 中仍有旧 `generated/cards/...` 路径，不可覆盖正式路径。`source_card_id` 和 `tts_card_id` 只用于追溯。

## 3. `SetupCatalog` 的关系

随机设置牌不是实际参战、购买或计分的卡牌。需要显式描述“抽到某随机牌时应拿出哪些牌”：

```yaml
randomizer_id: TS-0147
group_kind: hero
group_key: sidhe
members:
  - {card_id: TS-0432, level: 1, count: 6}
  - {card_id: TS-0433, level: 2, count: 4}
  - {card_id: TS-0434, level: 3, count: 2}
setup_abilities: [TS-0147-A01]
```

此例可用 CSV 的英雄等级和 TTS 模组中希德牌堆的数量核对。它说明**数据形状**；正式映射必须逐组校验后才能进组局池。其他组可能只有两级、有四级、有同名不同数值的多张怪物牌，不能套用“每系列三张、每怪物组十张”的硬编码。

`SetupCatalog` 至少还需定义：怪物组牌单、村庄供应堆牌单及数量、基础牌供应、疾病牌堆配置、可抽的地下城特征与其二次牌池、环境互斥规则、守护者/陷阱/宝藏组、雷霆之石选择。供应数量以规则资料为准，`tts_copy_count` 只能用于发现差异；TTS 存档可能包含备用卡、展示卡或特殊情景牌。

验证要求：每个映射引用已存在的可玩 `card_id`；所有数量是正整数；英雄等级顺序明确；同一实例不能同时进入两处供应；随机设置抽取耗尽时必须有明确结果；某组若含未编译能力，应在组局前被报告或排除。

## 4. 规则模式与优先关系

第一阶段使用 `classic` 竞争模式，对应《飞龙尖塔》规则书第 2～20、24 页的标准流程；既有文档中的 `standard_competitive` 指同一基础规则配置。联机层提交的[冻结规则配置](00-engine-boundary.md)可修改默认组数或固定选中部分牌组，这些属于组局参数，不创建一种新的战斗模式。基础规则、具体卡牌、场景/环境以及选定扩展共同形成 `ruleset_profile`。规则书第 20 页允许具体卡牌覆盖通则；覆盖应以显式的替代规则或设置修改记录来源，而非在核心函数里散落卡牌 ID 判断。

例子：

- 通常只选一张雷霆之石，放在地下城牌堆底部 10 张中；`TS-0199`“放逐仪式”调整雷霆之石、末日之心的摆放和终局。
- `TS-0034`“腐化德鲁伊”、`TS-0035`“虫群”、`TS-0147`“希德”被选中时，使用特殊疾病牌堆。
- 合作与单人玩法分别使用新的模式配置；它们修改抽取数量、资源所有权或胜负判定，不应通过标准模式里的临时布尔开关混合实现。

## 5. 构建与版本固定

构建过程顺序为：导入 CSV → 验证 `SetupCatalog` → 编译系统与卡牌规则 → 生成兼容性报告 → 生成不可变的 `catalog_version` 与 `ruleset_version`。版本应与实际输入内容和编译器版本关联，文件名 `v0.3.2` 本身不足以证明运行包一致。每局保存这两个版本、选定的规则模式和完整的冻结组局配置，旧对局重放时加载原版本。

规则 JSON 目前与 CSV 有已知差异：722 条旧图片路径、`TS-0717`/`TS-0718` 的显示文本，以及公共牌背类型。名称、标签、二级分类和已核对的 13 项静态数值一致。构建器应输出差异报告：CSV 掌管展示资料，已确认的系统裁定掌管规则语义；不可静默改写 CSV。原 JSON 的 `cards[].abilities[].ast` 是草案位置，`is_executable_as_card_ability=true` 也不等于已通过编译。

## 6. 组局准入

一个配置可以只开放部分随机牌，也可指定固定组并让其余名额随机补足。必须在组局前验证固定组以及随机候选可能选出的**全部实际卡牌**都有可用定义、所需能力已编译且对应系统规则存在。无法满足时明确报告卡牌 ID、能力 ID 和缺少的参数/处理器；不能开始后再跳过某张牌的效果。
