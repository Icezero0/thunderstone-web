# 验证、变体边界与实施次序

规则引擎的正确性取决于**每个进入牌池的行为能否重现并解释**，不能用“已拆成 964 条能力”代表已可玩。本文件给出测试矩阵、首版范围和待裁定清单。源资料见 [索引](README.md)。

## 1. 测试分层

| 层 | 检查什么 | 代表性失败 |
| --- | --- | --- |
| 联机层与引擎交接 | 参赛者/座位与准备归联机层；冻结请求送引擎；结果交回并归档 | 引擎修改座位；改配置后旧准备仍有效；同一房间同时开两局 |
| 目录与编译 | CSV 空值/数值、ID 引用、组局映射、AST 参数、规则包版本 | 把空胜利点当 `0`；模板缺少倍数却标为可执行 |
| 纯状态转移 | 指令合法性、区域移动、费用、抽牌、升级与购买 | 一张牌同时在手牌和摧毁区；金币超支 |
| 基础回合流程 | 村庄、地下城、休整和清理的阶段顺序 | 购买前升级；休整中发动村庄能力 |
| 战斗与大厅 | 装备、免疫、光照、摧毁时点、补位、陷阱、守护者、终局 | 光照算成攻击加成；陷阱被跳过；突破重复触发 |
| 单牌与组合 | 每条 `READY` 能力的正常、失败和边界场景 | 已付不起代价仍抽牌；多个疾病触发重复摧毁 |
| 联机与重放 | 幂等、版本冲突、随机重放、快照恢复、可见性 | 重试命令购买两次；事件泄露牌库顶牌 |

高价值规则用“给定状态 → 指令/事件 → 新状态、事件、合法下一步”的固定场景。分别验证联机层的房间/准备流程，以及引擎的配置校验 → `SETTING_UP → PLAYING → SETTLING → COMPLETED`；双方交接契约见[引擎边界](00-engine-boundary.md)。卡牌能力测试必须注明卡牌/能力 ID、规则包版本、引用的规则书页码或人工裁定来源。数据导入与随机设置映射另做完整性校验，但不能把同一实现函数的返回值互相比对当作独立规则验证。

## 2. 规则书驱动的基础用例

网页版配置另需单独测试，不把它们误标为规则书通则：默认 8 村庄/4 英雄/3 怪物组；改成其他已允许数量；固定若干组并随机补足；固定占满名额时不额外抽该类随机牌；环境和其他地下城特征不占怪物组名额；内容集候选不足和固定组冲突时引擎拒绝启动请求，联机层展示错误并解除准备。首位玩家默认随机；指定玩家、上局唯一赢家和参赛房主由联机层解析为本局固定玩家，引擎验证该玩家在启动请求的列表中。上局平局或赢家未参赛时，联机层不能生成有效的该策略请求。

| 规则书位置 | 必须覆盖的行为 |
| --- | --- |
| 第 2～4 页 | 3 怪物组、途中地下城特征、4 英雄组、8 村庄组；底部 10 张加雷霆之石；开局陷阱/宝藏回到底部；初始牌组 6/2/2/2、起手抽 6 |
| 第 5、24 页 | 每回合只选一种行动；村庄“能力 → 金币 → 购买 → 升级”；地下城“准备 → 宣告 → 战斗 → 凯旋 → 补位 → 陷阱 → 突破”；休整至多摧毁 1 张 |
| 第 6、9 页 | 抽牌堆耗尽且仍需抽牌时才洗弃牌堆；购买进弃牌堆；升级不跳级、同卡不连升、民兵花 3 经验变 1 级英雄 |
| 第 8、11～16 页 | 装备数量和重量、超重脱落；普通/魔法攻击分别计算；疾病合法选择；倍数先于光照；光照每点减 2 攻击；战斗效果无论胜负发生 |
| 第 12～13 页 | 准备摧毁立即离场，战斗效果摧毁延迟；胜利得怪物与经验，凯旋购买可各用完整手牌金币 |
| 第 17～20 页 | 连续陷阱/宝藏、守护者阶层 0、突破只在进入阶层 1 时触发；雷霆之石立即终局及取得权；动态胜利点和同分裁决 |

边界样例：村庄效果摧毁一张提供金币的牌，金币阶段不再计入它；某英雄战斗中力量从 1 降到 0 又恢复，回合末仍只摧毁一次；光照超过惩罚时最终惩罚是 0 而非攻击加成。还需分别在 `TURN_WILL_START`、`TURN_STARTED`、`TURN_WILL_END`、`TURN_ENDED` 挂接测试能力，验证手牌、当前玩家和抽牌时点，若其中触发终局则停止后续普通流程。

## 3. 已有规则 JSON 的十个回归场景

参考 JSON 的 `tests_v032` 已给出下列场景，实施时转为可执行测试：

| 场景 ID | 要验证的关键点 |
| --- | --- |
| `zero-strength` | 战斗中力量到 0 只标记，回合末摧毁 |
| `strength-recovers` | 力量恢复不清除待摧毁标记 |
| `two-diseases` | 恶疫和疲惫不让同一英雄被重复摧毁 |
| `fatigue-negative` | 疲惫的力量修正为 `-2` |
| `rockfall-no-premature-stop` | 有牌可翻时，某轮没有英雄不提前结束 |
| `dragon-jaw-exhaustion` | 无牌可翻时正常终止循环 |
| `dragon-jaw-midround-stop` | 已摧毁第 3 把武器后立即停止翻牌 |
| `dragon-tongue-monster-ref` | 龙之语引用使陷阱进入大厅的那只被击败怪物 |
| `death-sentinel-self` | 死亡哨卫的阶层 0 判断指向自身，光环影响其他怪物 |
| `sidhe-setup` | 选中希德英雄类型时切换特殊疾病配置 |

还要补充腐化德鲁伊与虫群的特殊疾病组局测试，以及“放逐仪式”设置和末日之心终局测试；只测希德会漏掉 TTS 模组和卡面已明确的另外两处触发。

## 4. 状态不变量与组合测试

对每次 `Transition` 自动检查 [状态模型](02-state-model.md) 中的区域、所有权、资源、装备、待选择及终局不变量。按合法指令生成小规模随机对局序列，检查没有卡牌重复、负经验、无界补厅循环或非当前玩家执行。此类生成测试用于发现状态损坏，规则细节仍须由独立场景验证。

组合测试至少覆盖：多个环境/全局效果作用于同一战斗、主动能力支付后等待目标选择、战斗中连续获得疾病、英雄力量下降导致武器脱落、凯旋买牌后大厅补位、陷阱连翻导致新怪物突破、阶层 0 守护者阻止取得雷霆之石但不阻止立即终局。

联机测试用两名并发提交同一 `expected_version`，只允许一条成功；重复 `command_id` 返回原结果。配置或参赛者/座位变更由联机层清空全部准备；全员对同一版本准备后，才将有序玩家与冻结配置提交引擎；重复开始和重复结算不得创建两局或两份结果。保存并重新加载设置阶段或行动阶段的 `PendingChoice` 后，只有指定玩家能继续。以相同规则包、冻结配置、玩家顺序、随机种子和指令记录重放，比较状态散列；对每位玩家的投影和推送事件检查隐藏牌库、未展示手牌与私有候选没有泄露。完成结算后，联机层将房间回到闲置，上一局结果仍可查询，新一局获得不同 `match_id`。

## 5. 合作与单人变体

规则书第 22～23 页的合作变体会改变怪物组数量、共享经验、怪物随回合推进、休整时玩家间传牌以及团队胜负。它不是在标准模式上只加一个“合作”标志就能运行：需要独立的 `ruleset_profile`、团队资源区、推进计时与多玩家选择流程。

规则书的“黑暗独行”变体还引用《元素之怒》的标准单人规则，当前本地这份 PDF 没有完整给出所依赖的基础单人规则。因此不能仅凭第 23 页实现完整单人模式；需要取得并确定该基准规则后另写规范。首版只允许明确支持的标准竞争模式，其他模式显示“尚未实现”，不自动落回标准规则。

## 6. 实施顺序与完成条件

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| 0. 规则资料与交接 | 已核对的 `SetupCatalog`、卡牌/规则包加载器、编译状态报告、`StartGameRequest` 校验器 | 能列出每张随机牌实际对应卡组；引擎只接收冻结请求，阻塞能力不能混入可玩牌池 |
| 1. 基础内核 | `GameState`、区域移动、随机、回合边界时点、合法行动、抽牌/购买/升级 | 从指定/随机混合设置进入首回合并完成一局最小经典对局；关键基础规则测试通过 |
| 2. 战斗与常见能力 | 装备、光照、物理/魔法攻击、战斗效果、大厅、触发/选择 | 可解释战斗账本；连翻、守护者和终局测试通过 |
| 3. 全量卡牌推进 | 按能力 ID 编译复杂控制流及特殊设置，并逐张测试 | 所选完整内容集的每张牌均为 `READY`；不以“已原子化”代替测试覆盖 |
| 4. 联机接入 | 房间/对局存取、幂等请求、玩家投影、实时更新、断线恢复 | 版本冲突、重放、隐藏信息及结算回闲置测试通过 |

只要还有未编译能力，仍可用经过验证的受限内容集开发和游玩；需要对玩家明确展示这局允许的内容集。扩大内容集时先完成规则编译与测试，再允许随机设置选中新增牌。

## 7. 待裁定清单

1. 每组怪物、英雄、村庄与特殊地下城特征的完整实例数量及随机牌映射；典型配置不能代替所有扩展的例外。
2. 多个同时触发或替代效果的选择者和先后顺序，尤其是效果改变大厅、战斗后延迟摧毁与凯旋的交互。
3. 特殊场景、环境和其他扩展与《飞龙尖塔》标准规则的冲突处。逐条记录卡牌/规则出处和最终测试，不按 TTS 物理摆放自动决定。
4. 合作、单人等非标准模式的产品范围与完整规则来源。

这些项目不会阻止第一阶段按已确认的标准规则构建受限牌池，但相应未裁定卡组不得宣称已可运行。
