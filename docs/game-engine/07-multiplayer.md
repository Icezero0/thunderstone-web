# 异地多人联机与持久化

联机层持有房间、参赛者/座位、配置草稿、准备状态，以及每局的持久化记录。TypeScript 游戏引擎只接收冻结后的启动请求和本局指令，产出组局状态、规则事件及结果；边界见[交接契约](00-engine-boundary.md)。引擎不感知 HTTP、WebSocket、数据库连接或登录会话。局内状态见[状态模型](02-state-model.md)，合法指令与能力结算见[回合流程](04-turn-flow.md)和[能力运行时](06-ability-runtime.md)。

## 1. 请求契约

```json
{
  "match_id": "...",
  "command_id": "由客户端生成且本局唯一",
  "expected_version": 42,
  "action": "UpgradeHero",
  "payload": {
    "source_instance_id": "...",
    "target_card_id": "..."
  }
}
```

上例是 `PLAYING` 中的对局指令。`actor_id` 从经过验证的会话取得，不相信客户端在 payload 中自称的玩家身份。请求只携带目标实例和选择，不携带金币余额、战斗胜负、抽到的卡或修改后的状态。服务器先确认玩家在本局且有操作权，再从当前状态产生 `legal_actions` 并验证具体参数。

房间指令另以 `room_id`、`room_version`、`config_version` 和 `command_id` 提交，至少包括确定参与者/座位、修改规则配置、准备/取消准备、请求开局、取消配置和查看结果。**这些指令由联机层处理，不转成游戏引擎命令。**联机层在参赛者全员对同一配置版本准备后，生成一次 `StartGameRequest`；游戏引擎校验并执行 `SETTING_UP`。局内设置选择和回合指令才送入引擎。任何配置、参赛者或座位变更使联机层记录的准备状态失效。

## 2. 一局单写入的提交过程

```text
读取快照 + 已提交版本
  -> 校验 command_id 是否已经处理
  -> 校验 expected_version 与行动玩家
  -> 调用纯规则内核，得到 Transition
  -> 校验新状态不变量
  -> 原子保存新快照、事件、command_id 与新版本
  -> 提交成功后按玩家权限推送视图
```

联机层对同一房间的状态转换和同一局的游戏指令实施单写入约束。可使用存储层的版本比较并交换或事务锁实现；两个玩家同时请求同一版本时只有一个能成功。相同 `command_id` 重发返回原提交结果，不重复准备、组局、购买、支付费用、洗牌或结算。旧版本请求返回冲突及当前可见版本，客户端刷新后再选择。不同房间可以并行处理。引擎仍检查其收到的状态版本和行动合法性，但不承担跨请求锁和数据库事务。

游戏引擎的建议接口：

```python
def validate_config(request: StartGameRequest, catalog, ruleset) -> ValidationResult: ...
def start_game(request: StartGameRequest, catalog, ruleset) -> SetupTransition: ...
def resolve_setup_choice(state, choice, catalog, ruleset) -> SetupTransition: ...
def legal_actions(state, actor_player_id, catalog, ruleset) -> list[ActionSpec]: ...
def apply_command(state, command, catalog, ruleset) -> Transition: ...
def settle(terminal_state, catalog, ruleset) -> MatchResult: ...
def project_state(state, viewer_id, catalog) -> PlayerView: ...
```

`SetupTransition` 与 `Transition` 包含新状态、可记录事件、可能的 `PendingChoice` 与必要的可解释计算结果。`viewer_id` 是已由联机层鉴权并映射的本局玩家 ID。联机服务不能绕过引擎直接改抽牌堆或玩家经验点；引擎也不能更改参赛者、座位、准备标志或房间状态。现有其他 TypeScript 项目的身份、房间或 API 基建可以复用，但规则判断保持在这个独立边界内。

## 3. 随机数与重放

开局确定随机数种子和算法版本，对局状态保存随机生成器状态。组局抽随机牌、洗混地下城、各玩家洗牌、随机目标等都只通过内核提供的随机接口进行；每次记录事件的随机用途、候选集合以及实际结果。不得用进程全局随机数、系统时间或客户端上报的“抽到某牌”决定规则结果。

相同目录版本、规则包版本、设置请求、随机种子和已接受指令序列，应重放成相同状态。持久化可以采用周期性状态快照加按序追加的指令/事件日志；恢复时从最近快照继续，并验证后续事件或重新执行指令。`catalog_version`、`ruleset_version` 和随机算法版本须保留，否则代码更新后旧对局无法可靠恢复。

## 4. 状态与事件的可见性

完整服务端状态不能原样发给任一玩家。每位玩家获取独立投影，规则书要求公开的内容才进入公共事件：

| 信息 | 开始选择行动前 | 村庄/地下城展示后 | 休整 | 终局 |
| --- | --- | --- | --- | --- |
| 当前玩家手牌 | 仅本人 | 已展示牌对所有人可见 | 未展示牌仅本人 | 用于公开计分的牌可展示 |
| 抽牌堆顺序 | 不公开 | 不公开，除非效果明确展示指定牌 | 不公开 | 可按计分展示牌单，无须公布原堆顺序 |
| 弃牌堆与大厅 | 依桌游公开区域 | 公开 | 公开 | 公开 |
| 私有选择候选 | 只给选择者 | 只给选择者，除非效果要求公开 | 只给选择者 | 不适用 |

展示某牌不会改变它仍在手牌中的规则语义。为用户显示的“抽牌”“摧毁”“公开手牌”等事件应经过同样的可见性裁剪，不能只隐藏状态快照却在事件 payload 中泄露未来牌库顺序。日志的内部完整版本可供服务器重放，玩家事件版本只含其有权知晓的信息。

## 5. 断线与待选择

能力、同时触发、并列最高价供应等都可能等待指定玩家选择。`PendingChoice` 和 `resolution_frames` 随状态事务保存；断线后登录同一玩家账号，可重新取得合法候选及尚未完成的行动。其他玩家只看到允许公开的等待提示，不可代选。选择提交时先重新验证候选、费用和目标区域；状态版本不匹配时拒绝旧选择。

如果玩家长时间不回应，超时或托管策略属于产品规则：要么等待，要么在开局前约定自动选择机制。第一阶段不应在未获同意时私自以最低卡牌 ID、随机目标或“跳过”代替玩家选择。

## 6. 存储边界

引擎使用抽象的快照和事件结构，由联机层的存储适配器持久化。联机层保存房间、参与者与座位、配置草稿/准备版本、启动请求、顺序事件/指令日志、幂等键和归档结果；每局另保存冻结配置、固定的目录/规则版本、完整 `GameState` 快照和最后提交版本。上一局赢家的身份必须从联机层已保存的结果解析，再把本局具体 `player_id` 交给引擎；不能由客户端上报赢家。卡图和卡牌定义可由版本化静态资料读取，不需要每局重复写入全部 722 张牌定义。

数据库产品、部署位置和 Web 框架在接入阶段再决定；联机层无论选型如何，都必须支持**同一事务中**保存版本、新状态、事件与幂等记录，并在归档结果后解除房间的活动对局关联。先完成纯引擎的规则测试和序列化/恢复测试，再接 HTTP 与实时推送。

## 7. 服务端错误分类

| 错误 | 返回给玩家 | 服务器处理 |
| --- | --- | --- |
| 非当前玩家或无权代选 | 明确的非法操作 | 不改变状态，不记录为游戏事件 |
| 版本过期 | 当前可见版本，要求刷新 | 保留旧提交结果，避免双重执行 |
| 资源或目标已变化 | 可读的合法性原因 | 保持状态不变 |
| 未编译规则或状态不变量失败 | 对局暂不可继续的错误 | 保留原快照与诊断信息，不能吞掉该效果继续游戏 |
| 对局已结束 | 返回终局视图 | 不再执行普通回合命令 |
