# 客户端同步与即时操作

服务器保存唯一权威对局。浏览器用共享引擎对公开输入作一次纯计算，暂时展示结果；不持有第二份独立游戏存档。刷新后以服务器结果恢复。

## 更新与旧对局兼容

引擎的 `ENGINE_VERSION` 是源码构建散列，用于前后端预览一致性和检测一次操作期间的热更新，不作为存档兼容版本。`Match.engine_version` 保留创建本局时的构建记录；读取旧局不改写数据库，正式提交队伍时由服务器绑定当前运行引擎的构建号。

持久化状态使用独立的 `state_format_version`，当前为 `1`。此前没有该字段的 TypeScript 存档按第一版格式读取，通过当前状态校验后可继续；下一次成功操作会写入版本标记。只读查询、失败操作不修改原始存档。历史撤回与跳转使用相同规则。若未来改变状态或解释器续体结构且无法兼容，必须在 `engine/src/state-format.ts` 增加显式迁移，不能只提升版本后丢弃旧局。

继续保留本局冻结的卡牌目录，严格核对 `effects_version` 与规则版本，不把旧存档静默套用到不同的卡牌效果定义。当前尚不自动迁移效果定义变更；不兼容格式、效果版本变更或引擎离线时，响应区显示原因，仍允许导出存档和浏览历史。普通代码修复或展示投影更新不再强制重开对局。

每次计算前后仍核对当前运行版本，若计算途中部署了另一个构建，则拒绝写入并提示重试。浏览器与服务器构建不同时仍禁止使用旧预览／即时预测结果，应刷新页面加载新前端。

## 通信与计算成本

- 编译规则按卡牌内容、规则文件时间戳/大小、引擎构建缓存，最多四份；变化后重新编译。
- Python 与 Node worker 用内容散列引用静态目录/规则。首次发送完整定义，随后只传引用和当前状态；淘汰或重启后自动重新登记。不缓存对局状态。
- 回合选项、状态标记、战斗准备投影在一次 worker 请求中返回。
- 新的 `matches.events` 只保存最近一步的事件。历史节点仍保存完整规则状态，事件只保存本步新增部分。`presentation` 保存当前公开手牌和翻牌区域的显示上下文，避免扫描整局日志判断可见性。
- 常规响应只返回游标之后的事件与动画。历史列表打开时才请求，之后只补充新增摘要；摘要查询不加载完整快照。
- WebSocket 同版本通知合并，自己的 POST 已收到该版本时不再重复 GET。操作提交期间延后刷新。

GET `/matches/{id}?compact=true` 获取基线，响应 `sync.event_sequence` 是事件游标。后续 GET 使用 `after_event`、`epoch`；POST 在 `sync` 对象内传同名字段。`history_after` 为空时不返回历史摘要。首次请求、历史 epoch 改变或游标超前返回 `sync.reset=true`，恢复当前牌桌，不播放历史动画。

`GET /matches/{id}/history` 只对参与者返回摘要。旧客户端不使用 compact 时仍读取完整事件和历史；导出沿当前历史分支重建完整事件。撤回不删除其他分支。

## 当前可预测范围

`engine/src/turn/prediction.ts` 的 `projectActionPrediction` 只输出自己的手牌/弃牌/控制区、公开大厅/供应/环境及所需卡牌字段。随机种子、抽牌顺序、其他玩家隐藏手牌、私有解释器续体均不输出。

`predictAction` 复用正式 `applyCommand`，当前支持：结束村庄效果并生产金币；不触发额外效果的购买和升级；跳过购买、升级或休整摧毁；普通休整摧毁。

初版采用保守边界：正在处理效果、复杂实例状态、持续/注册效果、随机补充供应等情况不给预测输入；有购买/升级触发器时对应操作等待服务器。结束回合抽牌、随机翻牌、主动 DSL 效果、战斗及其他玩家响应也不预测。预测不消耗真实 RNG，前后端引擎构建号不一致时放弃预测。

普通参战选择和装备草稿由战斗预览维护，不逐次通信。立即触发效果的特殊装备仍提交服务器；使用效果或提交队伍前同步普通装备方案。

## 队列、动画与纠正

战斗演出由 `battle_resolved` 驱动：最终攻击、魔法攻击、有效攻击、生命值、胜负及大厅位置来自引擎，参与者仅投影卡牌定义编号。点击确认的本地闪光只是操作反馈，不预测胜负。结果确定后由独立的 `BattleMotion` 图层播放自绘斩击／能量束：对攻击者本人从手牌区中心发出，对其他观看者从攻击玩家的头像位置发出；物理轨迹耗时 220ms，魔法能量束耗时 300ms。两类尺寸分别按各自攻击值递增缩放，40 点封顶。命中后播放短暂停顿与回弹，最后显示 1.8 秒的胜负提示，再按原事件顺序处理凯旋、摧毁标记、怪物离场与补位。需要玩家选择时不会提前攻击；刷新不重播历史。跳过、切后台及窗口尺寸变化会清除特效并恢复最终牌桌，减少动画偏好则直接展示结果。

战斗特效采用 DOM/CSS 与 Web Animations API，不依赖 WebGL、运行库、图片素材或音轨。轨迹、命中斩痕／光环与胜负提示由同一个演出对象管理，跳过和销毁时统一取消全部动画并移除元素。自动测试验证来源与目标位置、攻击数值缩放、事件先后及中断清理；视觉效果由用户手动验收。

`frontend/src/pages/match/command-queue.ts` 区分已确认基线、暂时显示的预测和待提交命令。

1. 确定的结果立即显示，产生的事件交给已有动画入口。
2. 命令带唯一 ID，后台按顺序提交，每次使用最近确认的版本。
3. 动画完成后可继续操作，不等待前一请求。未知结果的操作排在队尾，等待权威响应时停止后续输入。
4. 确认相同预测时不重播动画，不把画面退回更早的一步。
5. 预测不同或请求失败时，停止依赖它的未提交命令，恢复服务器结果；读取权威结果也失败时保持禁止操作并提示刷新。
6. 相同基线下手动重试保留同一命令 ID 和完整请求，避免响应丢失导致重复购买。撤回、跳转、取消和导出等待提交完成。

操作说明旁显示同步状态。客户端不永久保存待提交命令；关闭页面后，未提交的本地操作不会成为游戏结果。

## 更新与验证

后端启动自动应用 Alembic `0010_match_event_batches`，只增加可空字段，不重写旧历史。旧快照作为累计事件边界，新操作继续追加独立批次。引擎版本核对仍保留；更新构建后旧版本对局按原机制拒绝继续，应新开测试局。

测试覆盖公开输入边界、Node/浏览器与正式命令一致性、慢请求连续操作、未知结果屏障、重复请求、失败恢复、动画不重播、撤回分支和旧数据兼容。

24 回合/72 条命令的最后一轮本地进程内样本中，普通回合结束响应从 17,001 到 17,099 字节；末尾完整响应为 74,594 字节。首末九条命令中位耗时约 140/129 ms。随机开局的卡组会影响总大小；这不包含 VPS 网络延迟，也不是所有卡组的性能上限。历史仍保存完整状态，当前牌数、复杂效果和显式导出各有成本。
